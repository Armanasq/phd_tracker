# PhD Atlas — Unified PhD Application Workspace

The application tracker, Copilot, agent editor, model connections, workflows, and operational settings now share one interface, route table, and design system. AI Studio is no longer a separate frontend or iframe; old links redirect to the corresponding workspace route.

## Runtime separation

`https://armanasq.github.io/phd_tracker/` hosts the public, evidence-backed tracker. It stores no cloud model credentials. Its browser-only Copilot can connect directly to a user-configured localhost OpenAI-compatible model after a successful inference probe. For private agents, durable workflows and application state, start the private Python service on the machine running Ollama, vLLM, LiteLLM, LM Studio or your cloud credentials:

```bash
python -m phd_agents serve --port 8765
```

Open `http://127.0.0.1:8765/#settings` for functional Settings and automatic agent execution in the same interface.

## Model setup

1. Open **Settings → Connections**.
2. Select an existing runtime or **Add endpoint**, with an OpenAI-compatible `/v1` URL, provider name and installed model identifier. Examples: `http://127.0.0.1:4000/v1` for a locally running LiteLLM gateway, `http://127.0.0.1:8000/v1` for vLLM, or the actual `https://RESOURCE.openai.azure.com/openai/v1` for Azure.
3. Supply the private API key if required, optionally discover available model IDs, and use **Save, test & activate**. Actual inference must succeed before a connection is activated.
4. On cloud connections, explicitly check the applicant-data disclosure approval. This authorization applies only to the selected provider and can be revoked.
5. Use **Settings → Model routing** to assign per-agent overrides. Without an override, agents use the active workspace model automatically; no per-run provider choice is required.
6. Customize built-in agents or register new agents under **Settings → Agent builder**. Edit instructions, allowlisted tools and model assignments. Configure scheduled multi-stage workflows under **Settings → Automations**.

Local runtime availability, credentials and API response health are distinct. A listed provider preset does not imply a working service. Provider changes invalidate stored health and revoke automatic cloud approval. Keys live in the private runtime, not the static site; local saved keys are protected by file permissions, not encrypted at rest. A model response is an unverified proposal and never sends email or submits applications.

## Preserved application workflows

All earlier tracker sections remain available: Dashboard, Applications, Actions, Calendar, Pipeline, Contacts, Updates, Compare, Verification, Archive and Sources. The evidence snapshot is generated by `scripts/build_workspace.py` and retains the workbook's existing provenance. The browser never silently commits changes to public source records.

Owner edits on public Pages can still be staged locally and submitted through the authenticated Action Center issue. Private service operations use a separate local SQLite database. Browser reminder notifications require the tab to remain open; scheduled source notifications rely on existing GitHub Actions workflows.

## Unified private applicant operations

The **Operations** route now includes owner-maintained application state, referee records and reference-request states, distinct deadline clocks with verified source/time-zone fields, claim-level evidence, private research profile and capacity scenarios. These are accessible through the same navigation and backend as model Settings and Copilot. Select **Manage privately** on an application to inspect and update its private state with an optimistic version check. Changes to private records do not silently publish on GitHub Pages. Previously recorded source claims remain separate from owner-entered evidence and contradictions remain flagged for review.

## Per-model execution parameters

Each provider configuration now supports a bounded request timeout (10–180 seconds), an output-token ceiling (64–16,384), and an optional sampling temperature. Temperature is omitted from the wire request unless explicitly configured, because some reasoning models reject that parameter. Token limit parameter compatibility remains configurable for providers that use `max_completion_tokens` instead of `max_tokens`. These defaults are per provider and persist for all agents using that route.

## Prioritized proof obligations

The Operations control center includes a deterministic evidence work queue. It ranks recorded missing cutoff verification, source review, document readiness, submission receipts, referee portal confirmations and conflicting evidence claims using explicit task weights and deadline proximity. Every row links to the appropriate editor. Scores are **heuristic triage scores**, not admission probabilities or validated requirements; all claims remain provisional until independently verified.

## Public evidence coverage

The Sources view includes the original workbook's worksheet-level inventory, curated application records, reviewed opportunity notes, historical exclusions, the operational task projection and discovery-feed health. Historical audit dates remain attached to their respective counts. The Verification view now exposes deterministic proof obligations with category filters, incremental results and a CSV export of all checks.

These features operate on the committed snapshot and explicit browser drafts. They do not search live university portals when a view is opened, and they do not automatically submit applications or disclose private provider keys. Use the release manifest and corresponding GitHub Actions run to establish which source commit was actually published.

Validation additions: node --test tests/assurance.test.mjs and node --check site/modules/assurance-view.mjs.

## Complete workbook task inventory

The Task ledger route provides full history and upcoming workbook steps through a read-only, provenance-bearing table. Entries retain original worksheet and row, source task identifier, related opportunity, date, type, status and sanitized action text. The priority Actions route remains a shorter operational view. Ledger exports do not contain private mailbox URLs or raw personal email addresses.


## Responsive layout contract

The shared phone/tablet layout is governed by the final, ordered stylesheet \`responsive.css\`, loaded after component styles. It normalizes content gutters, 2-column metric-card padding, header/selector alignment, document tables, source cards, dialog bounds, and browser touch controls across the entire workspace.

The original root defect was an older higher-specificity \`:nth-child()\` selector zeroing the padding of metric cards, combined with a narrow-header \`flex-wrap:wrap\` rule. Both have been removed. The six-width Playwright regression checks in \`tests/mobile_layout_audit.cjs\` cover all 18 routes (108 route/viewport combinations) and fail for horizontal page overflow, inconsistent card padding, clipped deadline titles, wrapped header navigation or content crossing the shared page gutter. Internal calendar and kanban horizontal scrolling remains intentional.

The strict mobile regression also found and fixed a separate 768px breakpoint error: the fourth metric card inherited an obsolete zero-left-padding selector. The shared responsive layer now explicitly normalizes metric-card inline padding through the tablet breakpoint, and the fast geometry audit runs before the slower full route suite.

Visual screenshot review additionally detected an inherited `grid-column: 1 / -1` rule incorrectly expanding the last card in even-sized KPI collections. The new layout resets the final card to normal grid placement and only spans the row for odd-sized collections. The browser audit now enforces this invariant for all routes at phone widths.

## Repository-independent local and GitHub Pages deployment

The same static frontend can be hosted locally or published by another GitHub account. The Pages build derives repository identity from `GITHUB_REPOSITORY` and rewrites canonical metadata, sitemap, source/issue links and the commit-linked stylesheet. Forks must replace inherited public source data and create their own owner Action Center. No private model credential or SQLite state is ever hosted on Pages. See [self-hosting and fork setup](../docs/SELF_HOSTING.md).

Independent GitHub forks start in a blank `starter` data mode; the owner must replace/review source evidence and explicitly set Actions variable `PHD_ATLAS_DATA_MODE=source` before those records are served. Browser draft keys are namespaced per Pages repository path, preventing accidental cross-project state collisions; path-based keys are not a security boundary against other same-origin scripts.

## Deterministic submission readiness

The [Readiness view](./index.html#readiness) prioritizes verifiable next actions, cutoff proof, explicit preparation gaps, post-submission receipt checks and shared document demand. It runs without an AI key on Pages or locally. See [the readiness contract](../docs/READINESS_ENGINE.md).

## Evidence discovery and deployment routes

**Discovery (`#discovery`)** is an evidence-first research candidate queue. It distinguishes recorded source reviews, unresolved primary-source verification, staged promotions and recorded passed dates without inventing rankings or admissions availability. Candidates move into tracked applications only after explicit owner review and confirmation.

**Deployment (`#deployment`)** shows actual runtime capabilities. Static Pages, verified browser-local inference, private Python/SQLite and opt-in GitHub Actions have different permissions. Cloud hosting is explicitly unavailable until its authentication and data-isolation requirements are implemented.

The floating **Ask Atlas** assistant and Copilot share a single session-only browser model client on static Pages. On the private runtime the existing agent/tool client remains authoritative. The model-status chip reflects the active execution mode; it must not present a browser-only model as a private agent server. Local model configuration must pass an inference probe before use.

Hash routes, legacy aliases and invalid-hash recovery are specified in [the route coverage contract](../docs/ROUTE_COVERAGE.md). Private automations expose a read-only model-routing and cloud-disclosure preflight using `POST /api/workflows/preview`; no model is invoked until execution is explicitly requested.
