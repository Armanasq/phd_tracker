# Encrypted private backup export and isolated restore drill

The optional recovery extra (`pip install -r requirements-recovery.txt`) adds streaming scrypt + AES-256-GCM encryption. A private SQLite backup can be exported **outside the repository**, without loading the entire database into memory or exposing credentials in CLI flags.

1. First create a regular private backup with `python -m phd_agents backup`. Keep the reported SHA-256 digest in a secure, independent location.
2. Encrypt a verified backup using `python -m phd_agents encrypt-backup FILENAME --sha256 DIGEST --output /secure/offsite-staging.enc`. Enter a strong, unique high-entropy passphrase twice at the interactive prompt. It is never passed in command-line arguments or environment variables.
3. Move only the encrypted file to independent off-host storage using your organization's approved channel. Verify file ownership, remote access policy, retention and independent recoverability. **This application does not upload to cloud storage or claim that such a copy exists.**
4. After retrieving the encrypted copy onto a POSIX recovery host, run `python -m phd_agents drill-encrypted-backup /secure/retrieved.enc --sha256 DIGEST`. Enter the passphrase. The command authenticates the entire ciphertext, verifies the independent SHA-256 digest and SQLite schema/integrity in an owner-only temporary directory, and cleans up the plaintext automatically. The live database is never replaced during this drill.
5. To replace private state from the retrieved encrypted archive, stop the local API, worker and scheduled processes, then run `python -m phd_agents restore-encrypted-backup /secure/retrieved.enc --sha256 DIGEST --confirm`. The command requests the passphrase interactively, authenticates the ciphertext and recorded digest, verifies SQLite integrity and schema, then uses the existing exclusive-lock, pre-restore preservation and atomic replacement path. Without `--confirm` it refuses to proceed. Ordinary plaintext backups still use `restore-backup --confirm`. The encrypted file need not first be copied into the private backup directory. No provider credential is restored.

**Threat model and limits:** The format is versioned as `PHDAIENC1`, with a fresh random 16-byte salt, 12-byte GCM nonce, AES-256-GCM authenticated stream and scrypt (`N=131072,r=8,p=1`). The export also rechecks the backup SHA-256 and byte length *while streaming the bytes to encryption*, rejecting any changes since the initial SQLite verification; source files are reopened without following symlinks. Partial encrypted outputs are removed on failure. The ciphertext is authenticated against its versioned header; incorrect passphrases and tampering fail before the decrypted database is trusted. Security depends on the passphrase's entropy, local host compromise resistance and the safety of off-host storage. This format is currently a private PhD Atlas recovery artifact, not a standardized portable archive. The encrypted export does not include provider credentials, which must be independently reconfigured.

The CI regression `tests/test_phd_encrypted_recovery.py` exercises genuine cryptographic round trips, tampered ciphertext, wrong keys, file permissions, active SQLite-lock refusal, preserved previous state, and fresh isolated owner recovery. Authenticated decrypted data and the pre-restore safety copy are temporarily stored as owner-only plaintext within the private state directory; ensure the host protects this directory and secure its backup retention. It does **not** validate a production user's off-site object, backup retention policy or organization-specific disaster recovery plan. Therefore the encrypted **off-host** restore acceptance criterion in Issue #6 must remain open pending an actual operator-run remote recovery exercise.
